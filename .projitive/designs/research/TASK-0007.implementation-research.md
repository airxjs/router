## Code Architecture and Implementation Findings

### Signal State Creation (`source/router.ts#L50`)

```typescript
const currentElement = createState<AirxElement<RouteComponentProps> | null>(null)
```

**Finding**: `currentElement` is the sole reactive state in Router. It holds the entire rendered element tree.

### Signal State Update (`source/router.ts#L103`)

```typescript
if (matchResult == null) return currentElement.set(null)
```

**Finding**: When no route matches, signal is set to `null` synchronously.

### Signal State Update (`source/router.ts#L143`)

```typescript
if (!isRedirected) currentElement.set(createRouteElement(matchResult))
```

**Finding**: After redirect handling, the element is set. This is the primary signal write path.

### History Callback (`source/router.ts#L144`)

```typescript
history.listen(data => handleHistoryUpdate(data.action, data.location))
```

**Finding**: History listener calls `handleHistoryUpdate` synchronously. Multiple rapid history changes could cause race conditions in signal updates.

### Signal Global Singleton (`source/signal.ts#L19-L29`)

```typescript
function getSignal() {
  const globalSignal: typeof Polyfill = globalNS['Signal']
  if (globalSignal == null) throw new Error('Signal is undefined')
  if (firstSignal == null) firstSignal = globalSignal
  if (firstSignal !== globalSignal) throw new Error('Signal have multiple instances')
  return globalSignal
}
```

**Finding**: The signal polyfill is lazily loaded from the global namespace. If `airx` or another package initializes a different Signal instance, Router will throw. This is a critical compatibility risk.

### Signal Watcher Not Used

The Router uses `createState` but does NOT use `createWatch`. There is no watcher to detect missed updates or external signal modifications.

### Relative Redirect Path Resolution (`source/router.ts#L109-L112`)

```typescript
if (!isAbsolute(matchResult.route.redirect)) {
  targetPath = joinPaths(matchResult.fullPath, matchResult.route.redirect)
}
```

**Finding**: Redirect paths are resolved relative to `fullPath`, which includes the matched path prefix. This may interact unexpectedly with nested routes.

## Implementation Plan

### Phase 1: Audit Signal Dependencies

1. Document all `createState`, `createComputed`, `createWatch` usages in router
2. Identify external signal sources (airx runtime, signal-polyfill, global)
3. Map signal read/write cycle during navigation

### Phase 2: Identify Regression Risks

1. **Race condition risk**: Rapid history changes during signal update
2. **Signal identity risk**: Multiple Signal instances across packages
3. **Nested route signal propagation**: Parent/child route element creation order
4. **Redirect timing**: Sync redirect during history callback may double-fire
5. **Global namespace pollution**: `Signal` key could be overwritten

### Phase 3: Define Regression Test Plan

| Test Case | Description | Acceptance Criteria |
|---|---|---|
| TC-1 | Single route renders correct component | Component receives correct `data.params` |
| TC-2 | Nested route renders parent + child | Both components render with correct hierarchy |
| TC-3 | Redirect route triggers history.push | Browser URL changes, no component rendered |
| TC-4 | Relative redirect resolves correctly | `/a/b` redirect `'c'` → `/a/b/c` |
| TC-5 | Rapid navigation (Navi A → B → A < 16ms) | Final state is consistent, no partial render |
| TC-6 | `useRouter()` returns same history instance | Multiple calls return equal references |
| TC-7 | No-match path sets currentElement to null | `currentElement.get() === null` |
| TC-8 | History mode (hash vs browser) parity | Both modes handle redirects identically |

## Risks and Open Questions

### Risk 1: Signal Version Fragmentation
If `airx` upgrades its signal-polyfill version independently, the global `Signal` check may fail.
**Mitigation**: Pin signal-polyfill version and add integration test.

### Risk 2: Sync Redirect Double-Set
Calling `history.push()` during `history.listen()` callback may trigger another listener call before the first `handleHistoryUpdate` completes.
**Status**: Open — needs verification with test TC-5.

### Risk 3: Memory Leak from Listener
`history.listen()` returns an unsubscribe function that is never called in current implementation.
**Status**: Noted — out of scope for this research, flag for TASK-0006.

### Open Question 1
Should Router use `createWatch` to track signal dependencies explicitly, or rely on airx's rendering cycle?

### Open Question 2
Is there a defined signal lifecycle guarantee from airx that Router can depend on?
